# unseed

[English](README.md) | **Русский**

unseed восстанавливает строки из Java-классов, в которых ключ шифрования строк
зависит от имени вызывающего класса и метода, и умеет вписывать расшифрованный
текст обратно в классы. Это один файл на Python, которому нужна только
стандартная библиотека.

## Схема

Некоторые обфускаторы привязывают шифрование строк к тому, кто вызывает
дешифратор. Дешифратор находит вызывающий код в стек-трейсе и берёт имена его
класса и метода в качестве seed:

```java
static String d(String s) {
    StackTraceElement frame = new RuntimeException().getStackTrace()[1];   // вызывающий
    String seed = new StringBuffer(frame.getClassName())
                      .append(frame.getMethodName()).toString();
    ...
    out[i] = (char) (maskA ^ (s.charAt(i) ^ seed.charAt(n)));
}
```

Если расшифровать тот же шифртекст из другого места, получится мусор, поэтому
просто вызвать дешифратор на каждой константе не выйдет. Но вызывающий код
известен заранее: это класс, в котором стоит вызов (`this_class`), и настоящее
имя метода.

unseed выполняет линейный пролог дешифратора на небольшой стековой машине,
проходит по телу цикла, чтобы понять, какие константы XOR-ятся с символом, и
определяет порядок частей seed по тому, как собирается
`StringBuffer`/`StringBuilder`. Ни JVM, ни декомпилятор для этого не нужны.

## Границы

unseed работает только с этой схемой. Это не универсальный деобфускатор: он не
снимает Zelix, Stringer, Allatori или ProGuard, не переименовывает классы, не
распутывает поток управления и не убирает защиту от модификации. Для этого есть
[java-deobfuscator](https://github.com/java-deobfuscator/deobfuscator) и
[threadtear](https://github.com/GraxCode/threadtear).

Начните со `scan`. Если он пишет `0 frame-shaped`, в вашем jar этой схемы нет,
и unseed не поможет.

## Использование

Нужен Python 3.9 или новее. JDK не обязателен: он используется только для
сверки с `javap` и JVM. На вход подаётся `.jar`, `.zip` или каталог с
`.class`-файлами.

```sh
python3 unseed.py selftest                       # прогон встроенной фикстуры, ввод не нужен
python3 unseed.py scan     target.jar            # есть ли в jar эта схема?
python3 unseed.py strings  target.jar --json out.json --report out.txt
python3 unseed.py patch    target.jar --out work/ --copy-all
python3 unseed.py verify   target.jar --javap-check 50 --ground-truth 'строка, которая точно есть в jar'
python3 unseed.py indy     target.jar --worklist worklist.json
```

- `selftest` проверяет кодек и прогоняет встроенную фикстуру.
- `scan` считает дешифраторы, зашифрованные литералы и вызовы `invokedynamic`.
  Если в jar используется схема, которую unseed не поддерживает, он об этом
  скажет.
- `strings` расшифровывает все литералы и для каждого записывает класс, метод,
  индекс байт-кода, seed и шифртекст. `--grep` фильтрует вывод, `--json` и
  `--report` сохраняют его в файлы.
- `patch` записывает `.class`-файлы с подставленным текстом и манифест SHA-256
  каждого файла до и после. Пропатченные классы ведут себя так же и проходят
  верификатор JVM. С `--copy-all` копируются и нетронутые классы, чтобы дерево
  на выходе было полным.
- `indy` раскладывает вызовы `invokedynamic` на разрешённые лямбды,
  Java-bootstrap'ы, которые можно эмулировать, вызовы, упирающиеся в native-код,
  и вызовы с неизвестным владельцем. Те, что придётся снимать в рантайме, он
  записывает в список задач.
- `verify` запускает все проверки, какие есть в unseed, и полагаться стоит
  именно на него. Встроенную фикстуру он прогоняет первой, ещё до чтения ваших
  данных.

У `verify` есть ещё опции:

- `--javap-check N` сверяет декодер инструкций с `javap` на N классах.
- `--javap-attrib N` проверяет, что каждый литерал действительно лежит в том
  методе, который указал unseed. Это важно, потому что имя метода входит в seed.
- `--reference F` сравнивает результат с прошлым запуском `strings --json`.
- `--strict` превращает низкую долю печатных символов из предупреждения в
  ошибку.
- `--no-jvm` пропускает проверки на JVM; `--require-jvm` падает, если JVM нет.


## Что можно взять отдельно

Часть кода пригодится и вне этого инструмента.

- **Кодек modified UTF-8.** `CONSTANT_Utf8` в JVM хранит `U+0000` как
  `0xC0 0x80`, а символы за пределами BMP как суррогатные пары CESU-8.
  `decode('utf-8', 'replace')` в Python превращает и то и другое в `U+FFFD`, то
  есть незаметно меняет строку. `dec_modified_utf8` и `enc_modified_utf8`
  обрабатывают такие случаи правильно и падают на некорректных данных.
- **Декодер инструкций.** `tests/test_opcode_table.py` собирает классфайл с
  отдельным методом для каждого из 256 байтов опкода и сверяет мнемонику и
  длину инструкции с `javap`.
- **Патчер, не меняющий длину кода.** Каждое место вызова (`ldc <шифртекст>`,
  необязательный `checkcast` и `invokestatic` дешифратора) заменяется на
  `ldc_w <открытый текст>` с добивкой `nop`, так что размер кода не меняется.
  Смещения переходов, кадры `StackMapTable`, диапазоны исключений и записи
  `LineNumberTable` остаются верными без пересчёта. Новые элементы пула констант
  добавляются в конец, так что старые индексы не сдвигаются.

## Тесты

```sh
python3 -m unittest discover -s tests -t .
UNSEED_REQUIRE_JDK=1 python3 -m unittest discover -s tests -t .   # для CI
```

Без JDK тесты на JVM пропускаются. С `UNSEED_REQUIRE_JDK=1` они вместо этого
падают.

Фикстура в `tests/fixtures/` — синтетический класс, написанный по алгоритму
выше, без стороннего кода. Шифртексты для неё получены отдельно написанной
функцией шифрования (`encrypt_units` в `tests/make_fixture.py`), а не взяты из
вывода самого unseed. Тесты запускают скомпилированную фикстуру на настоящей JVM
и проверяют, что строки в точности совпадают с `expected.json`, включая
встроенный `U+0000` и символ за пределами BMP. Потом то же самое делается с
пропатченными классами. Если бы патчер изменил длину хоть одной инструкции,
верификатор JVM их бы не принял.
